## 关于上下文经验
1. 建议手动多记录Note，不然对于一个大型工程来说，你无论是加功能还是Debug功能，对话长了之后都容易出错，最好是针对每一项功能，落实成一个Note笔记，下次使用相似的功能的时候直接导入笔记内容（记得Review上一次保存的Note笔记保证里面都是正确和精简的核心内容）

## 关于新建工程
1. 可以使用superpower先进行brainstorm，但是brainstorm只能补齐你没有完善的细节，并不能把你的idea或者产品提升到一个更高的高度，你才是产品的瓶颈
2. Github有Design.md帮助你完善产品的页面设计，但是它大多是参考已有风格，如果你有更好的审美，建议自己调整或者实现
3. 研究型工作不能类比产品交付类的工作，不存在大量密集开发的功能点，而只是需要着重解决几类重点问题，ai-coding并没有加速这个训练过程，你需要做的神经网络训练你还是需要做。而不是像传统软件开发一样可以借助ai-coding快速拿产品结果。从这一点上面我认为研究型工作更加需要聪明的模型，而传统软件开发普通模型完全够用

## 关于原有大型工程
1. 虽然有些人不建议自动生成Claude.md但是我觉得如果你对已有工程很熟悉的话，完全可以自动生成，生成完自己手动修改不对的地方，并且持续迭代完善需要重点关注的地方，逐步完善Claude.md文件（初始化md文件这一步一定不要外包，确保你自己理解md文件的每一行）
2. 一定注意渐进式披露（注意Claude.md文件的长度，可以手动或者自动拆分），因为你每次开发功能也不是需要所有整个大工程的所有知识。
3. 许多大型工程往往因为过往程序员没有好好维护的意识而缺失UT或者存在大量的重复代码和相似文件。
4. 缺失UT建议逐步补齐，可以从小的功能点开始，因为AI coding之后写代码不是瓶颈，测试才是。
5. 大量的重复代码和相似文件我个人建议是需要把正确调用或者索引到的文件记录到Claude.md文件里，这个过程可以让Claude从函数的调用入口帮你完善查找整个链路索引到的代码，从而保证下次不会出错。不然你就会发现Claude经常随意grep代码进行查找，索引到错误的文件，给你错误的结论
6. 我不觉得远程Vibe Coding有多爽，盯着屏幕干活更加安心，效率和交付结果也更加可控

## 关于协作
1. 对于每一个功能点建议落实好本地md文件用来描述该功能，如果有同事协作也建议在更改代码的时候同步维护文档的功能点更新
2. 如果你的同事还在大面积的古法编程，对于你来说可能是更痛苦的事情。合并还有更新代码的维护成本很高。所以建议你每次对于你ai coding的代码一定要熟悉，不熟悉的话你可能会给古法编程的同事带去更多的麻烦，同时ai犯的低级错误如果你没有审查出来也会让你羞愧难当 ：)
